## 二、后台与数据能力

### 1. 登录身份与权限

- ✅ 标注后端通过统一身份服务校验登录令牌，并建立标注侧 HUMAN actor 映射；不复制统一登录密码。
- ✅ `/api/labeling/v1/me` 返回标注侧身份、能否创建项目和能否标注。
- ✅ 标注管理员可管理标注侧账号状态/管理员授权；这是标注角色，不修改训练平台全局 roleId。
- ✅ 项目 owner、领取者和提交人采用后端逐请求授权；不能只依靠前端隐藏按钮。
- ⚠️ 新增功能的项目权限边界尚未针对真实用户组合做完整线上回归。

主要代码：`labeling-service/src/main/java/com/tss/labeling/identity/`。

### 2. 项目与标注规范

- ✅ 创建项目、列出本人项目、读取本人项目、创建规范版本。

- ✅ 当前图片项目规范与图片分类结果格式相配；能耗项目类型和结果格式尚未加入当前后端代码。
- ⬜ 规范冻结的模板版本、输入/结果 schema ID 和摘要、兼容升级策略尚未完整落库。

- ✅ 单张样本草稿可保存并读回，使用 revision 防止覆盖较新的草稿。

- ✅ owner 可读取本项目提交列表和提交详情；提交者也可读取自己的提交。
- ⬜ owner 的“接受/修改/退回/再次发布”业务动作没有形成审核 API 和审计记录。
- ⬜ submission 与最终采用成果之间尚无独立的不可变版本模型。

主要代码：`labeling-service/src/main/java/com/tss/labeling/tasks/ResultService.java`；数据库 V5。

### 7. AI Agent 自动标注

- ⬜ AI 执行批次、样本范围快照、租约/重试/取消、进度和部分成功/失败清单。
- ⬜ AI 结果格式校验、模型/规则版本、真实置信度及执行证据存储。
- ⬜ AI 执行结果返回需求方工作台并与人工提交统一展示。

文档中已有设计和接口草案，但不能把文档里的接口当成已实现功能。

### 8. 需求方审核、置信度与多轮流程

- ⬜ 需求方逐样本查看、修正、确认、标记待修正并记录理由。
- ⬜ AI 结果按本次执行分布展示；需求方手动设置高/中/低阈值，预览后才可批量确认。
- ⬜ 未知置信度单独处理；阈值本身不等于确认；改阈值不得改变历史确认记录。
- ⬜ 低/中/未知置信度及有分歧样本的筛选、数量预览、携带或隐藏参考答案的再次发布。
- ⬜ 成功项和失败项分开；需求方能先处理成功项，再决定失败项重试或转人工。
- ⬜ 全任务最终完成的明确确认及成果列表。

- ⬜ 结构化 schema 文件、schema 摘要冻结、格式升级/兼容测试、未知字段策略尚未完成。
- ⬜ 行业标准尚未制定；当前 JSON 只是平台内部版本化格式草案，不应称为行业标准。
- ⬜ Label Studio 编辑器代码复用尚未完成。当前图片人工页面为平台自己的页面；没有将 Label Studio 整体服务纳入当前运行链路。

## 四、建议开发顺序

1. **先定义并实现公共插件契约**：明确模板版本如何绑定输入/结果schema、导入器、编辑器、校验器、完成规则和导出器；现有图片流程继续兼容。
2. **把能耗作为首个时序插件接入**：核对迁移后再实现 ZIP 导入、站点日列表/曲线、标签选择、草稿保存和按包完整提交。用交付数据验收该插件，不把它当成平台唯一支持格式。
3. **补齐需求方结果处理**：查看提交、逐条修订/确认、标记待修正、选样再发布并保留轮次历史。
4. **实现 AI 执行主链路**：先做统一 Agent 接口和真实可运行的第一个规则/模型 Agent，支持范围快照、部分成功、置信度、版本和失败重试；AI 结果先交需求方，不自动审核。
5. **实现置信度分档、集成与质检**：阈值由需求方配置；多数投票只生成建议；金标准、双标和抽检单独留痕。
6. **固定结果格式与导出**：先完成内部版本化 schema、JSONL manifest、能耗 CSV 映射和回读一致性，再与甲方讨论行业标准化。
7. **发布验收**：补充自动化测试；确认迁移顺序与备份恢复；提交前后端功能分支；确认 Actions 成功后，再核验部署版本和真实页面。
