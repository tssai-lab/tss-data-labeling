# 工业能耗标注需求待确认问题

日期：2026-11-10。用途：与老师、数据提供方及标注业务专家逐项确认能耗任务的标注语义和验收口径。本文记录问题和建议答案；**所有“建议”均未获确认，不作为冻结规范或开发验收依据**。确认后由A更新产品规范、模板schema、接口和验收用例，再通知B/C/D。

## 先确认的 P0 问题

| 编号 | 需要确认的问题 | 可供讨论的建议 | 影响 |
|---|---|---|---|
| P0-1 主标签 | `normal`、`idle_zero`、`partial_zero`、`low_load`、`high_load`、`spike`、`dip`、`missing`、`meter_fault`、`shift_change`、`holiday`是否仍是完整标签集？哪些可以同时成立？“正常”能否与“节假日”等场景标签并存？ | 区分一个必选主标签和可选补充标签；冲突不要靠标签顺序解决，先定业务含义 | 结果字段、编辑器控件、完成校验、AI输出、投票字段 |
| P0-2 无法判定 | 某天数据不足、业务背景不明或多条规则冲突时，标注员能否提交“无法判断/需专家核查”？是否属于正式答案？ | 允许显式的待确认状态或候选意见；未经业务确认不新增正式标签 | 人工能否完成提交、AI如何报告未决、抽检统计 |
| P0-3 标签粒度 | 主标签只描述“整日状态”，还是还要记录异常类型、点位、连续区间？`label_detail`想存自由文本、标签列表、触发依据，还是以上都要？ | 主标签＋补充类别＋结构化点位/区间＋备注分字段保存 | 时序UI、result schema、人工完成规则和导出 |
| P0-4 主次与冲突 | 同一天同时出现停运、尖峰、低负荷等情况，哪个作为主标签？一个样本能否有多个主标签？点位异常是否允许多个类型？ | 标签含义正交时允许多标签；若导出只容纳一个主标签，由业务方确定优先规则 | CSV映射、AI标签映射、多标注结果的一致性和集成 |
| P0-5 零与缺失 | `0 kWh`、空值、缺少某个小时、整日缺少记录分别表示什么？全天24个值为0能否标停运？ | 零值保留为有效观测；缺测单独记录，不能补零；业务含义由专家定 | 输入schema、图表断线/零线、`idle_zero`/`missing`判断 |
| P0-6 时间定义 | `hour_local=0`表示00:00开始的小时桶 `[00:00,01:00)`吗？业务日以北京时间自然日为准吗？区间结束时刻是否不包含端点？ | 固定Asia/Shanghai；点映射到小时桶，连续异常区间用半开区间`[start,end)` | 图表横轴、跨日区间、点位保存和交换格式 |
| P0-7 近30天基线 | 窗口是否为同一站点前30个自然日 `[d-30天,d)`，排除当天及未来数据？允许少于30天时最少需要多少有效日？ | 默认不看未来；不足时报告`BASELINE_INSUFFICIENT`，不据此输出normal | B需提供的历史数据范围、规则Agent输出和复现实验 |
| P0-8 分位数与相对阈值 | P5/P50/P99使用哪一种分位数插值算法？零基线下的50%/150%比例、异常跌落比较怎么定义？ | 固定算法/版本；分母为0或统计无效时不计算比例，返回未决及原因 | 同一输入在不同运行环境能否得到相同标签与依据 |
| P0-9 规则阈值 | `partial_zero`的06:00–22:00包含哪些小时桶？连续至少6小时如何计算？`spike`的P99乘数、`dip`的P5倍数、计量差异率的分子/分母、恒定值的容差是什么？ | 每条规则记录参数、单位、版本和命中窗口；由业务方提供或批准数值 | Agent是否可以启用、候选结果可否复核、测试期望值 |
| P0-10 班次与节假日 | 班次切换需要哪些时间窗口、阶跃幅度和重复次数？`holiday`如何区分法定假期、调休工作日、普通周末？使用哪版日历？ | 规则依赖的日历/配置文件版本随执行固定；没有依据时不判定 | 特征数据、日期标签、规则版本与历史复现 |
| P0-11 主表和层级 | 企业总表与设备表可能重叠。每个站点日独立标注，还是需要结合企业级表和关联设备共同判断？ | 标注单位仍是一站点一日；汇总报表按`total_basis`选择口径，不能将企业和设备数据直接相加 | 样本范围、AI上下文授权、统计和结果导出 |
| P0-12 人工自评 | 指南写`confidence`必填。人工要填数字、低/中/高自评，还是“未知”也可？这和AI模型confidence是否分开？ | 人工使用独立的自评字段，允许UNKNOWN；模型confidence只保存真实模型分数，不能相互换算 | 结果格式、分档页面、导出与质量分析 |
| P0-13 尖峰/跌落定位 | `spike`、`dip`、`meter_fault`是否必须标出具体小时或区间？整日异常能否不标点位？无点位时备注是否必填？ | 根据主/补充标签设置完成条件；显示标签时不自动生成点位 | 点位/区间控件、整包提交校验与专家复核 |

## 质检与验收问题

| 编号 | 需要确认的问题 | 可供讨论的建议 | 影响 |
|---|---|---|---|
| Q-1 金标准 | 指南建议500条金标准。谁有资格制定/确认？是否从2,000条样例中挑选？是否需要独立专家复核和版本？ | 金标准由业务专家逐条确认并冻结；规则Agent输出不能自动变成真值 | 质检权限、金标准版本、准确率报告可信度 |
| Q-2 抽检母体 | “其余任务至少20%抽检”是每项目、每轮还是每批？按2,000样例计算是否排除500金标准后，从剩余1,500抽300？ | 先固定母体、比例、抽样方法/种子、是否与双标重叠和复用规则 | 固定样本清单与覆盖率统计 |
| Q-3 双人范围 | “10%双人标注”的分母是全体2,000条还是非金标准部分？两人是否必须互相看不到标签、参考答案和对方答案？ | 首轮按全体2,000条的10%作独立盲标示例，金标准/抽检可重叠；最后以业务方确认为准 | 人工包的两席位、编辑器可见范围、统计样本量 |
| Q-4 一致性指标 | Cohen's kappa只针对单选主标签吗？多标签、点位、区间分别采用什么指标？目标≥0.70是建议还是验收门槛？ | 单选主标签先按配对结果计算kappa并显示样本数；多标签和定位任务另定指标；不可计算时说明原因 | 统计接口、指标解释、最终验收标准 |
| Q-5 分歧裁决 | 两人不一致时由谁裁决？第三人的建议是独立提交还是直接改最终答案？谁有权把结果确认成最终值？ | 第三份意见也保留来源；项目owner记录采用、修改及理由 | 人员权限、审计链、投票是否采用 |
| Q-6 批次规模 | 先验收2,000条样例，还是要求第一轮直接处理23,177条全量？全量导入时最大耗时/内存/并发目标是多少？ | 先在2,000条跑通格式和流程，再做全量容量验收；目标值由部署环境确认 | B的数据导入优化和项目验收排期 |
| Q-7 自动结果 | 规则Agent每条都必须输出标签吗？无规则命中、多条冲突、历史不足和模型失败，是否都能以未决/失败交回？ | 支持逐样本NO_DECISION/FAILED，保留原因；不把未知结果写成normal | AI部分成功、需求方处理和规则Agent验收 |

## 导入、格式与对外标准问题

| 编号 | 需要确认的问题 | 可供讨论的建议 | 影响 |
|---|---|---|---|
| F-1 首轮导入文件 | 首轮用`sample/station_day_tasks_2k.csv`作为任务样本，还是上传小时表、日表、站点/企业元数据后平台分组？样例与原始表同时出现时以谁为准？ | 先用2k宽表联调，再用hourly＋daily全量文件验收；preview/sample不重复导入 | 导入插件选择、文件检查与稳定样本ID |
| F-2 重复样本 | 同一个项目中，同一数据集的站点日通过不同导入模式再次出现，是拒绝、跳过还是建立新来源版本？数据内容修改后如何识别？ | 按数据集版本＋站点日查重；源内容变化创建新输入版本，不覆盖旧结果 | 幂等、版本与多人投票独立性 |
| F-3 结果格式 | 是否认可公共来源元数据与任务payload分层？是否以`annotation-record-v1`作为内部格式起点？未来是否需要导出Label Studio兼容文件？ | 内部ID与标签ID稳定；提供版本化JSON Schema和显式格式转换，不存私有UI结构作业务主键 | 数据库、AI/人工交互与导出兼容 |
| F-4 标准化范围 | 预期行业标准覆盖数据输入、标签语义、点/区间、置信度、来源/审核还是模型接口？由谁组织评审、采用何种发布/版本管理机制？ | 先完成两类任务验证，再和甲方/行业方共同确定标准范围；目前只称内部草案 | 避免过早冻结后难兼容的内部字段 |
| F-5 Label Studio映射 | 要求映射到哪一固定版本、哪种导入/导出格式？哪些类型需来回无损转换？`from_name/to_name/type/value`之外要保留什么？ | 固定版本后为图片分类和时序逐类型提供正反例及往返测试；不声称自定义时间类型是原生LS类型 | 编辑器接入与交换格式一致性 |
| F-6 置信度粒度 | AI置信度表示主标签概率、每个标签的分数、点位/区间置信度还是整条任务分数？不同Agent能否比较？ | 不同分数语义分字段并记录校准/来源；含义未知为null，不能跨模型直接共用阈值 | 需求方分档、模型评估和导出解释 |
| F-7 导出交付 | 最终CSV是否必须写回原`label/label_detail/annotator/confidence/notes`列？点位、区间、历史和AI失败是否同时交付JSONL/manifest？ | 保留原包只读；输出版本化机器格式＋CSV易读映射，人工自评与AI分数分列 | B的导出适配和下游使用 |
| F-8 数据与结果使用范围 | 数据集许可证限制下，确认哪些角色可下载原始CSV、标注结果、截图和脱敏示例？项目结束后返还/删除由谁执行？ | owner与受授权成员按样本范围读取；仓库不放数据，外发先核对许可 | 文件权限、留存周期和演示材料 |

## 讨论顺序与记录

1. 先定标签含义、主次关系、无法判断和必填规则（P0-1—P0-4、P0-12—P0-13），据此冻结第一版结果schema。
2. 再定时间、缺失、规则窗口、阈值和历史基线（P0-5—P0-10），据此判断时序输入和自动标注能否验收。
3. 确认金标准、抽检、双人比例、盲标和裁决（Q-1—Q-5），据此实现质检任务与指标。
4. 最后确认导入/版本、Label Studio映射、行业标准及数据留存（Q-6—Q-7、F-1—F-8），据此冻结API和交付格式。
